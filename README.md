## แนวคิดของ Domain

**ปัญหาจริง:** รีวิวสินค้าบน Shopee / Lazada / Flipkart มี noise เยอะมาก

- **สแปมโฆษณาแฝง** — รีวิว 5 ดาวที่จริง ๆ แล้วคือโฆษณา ทิ้งเบอร์โทร/LINE ID ไว้ขายของ
- **รีวิวปลอมสั้น ๆ** — `"ดีมากค่ะ"` ซ้ำ ๆ กันหลายสิบอัน ไม่ให้ข้อมูลอะไร
- **ข้อมูลส่วนตัวหลุด** — ผู้ซื้อจริงทิ้งเบอร์โทร/ที่อยู่ไว้ให้ร้านติดต่อกลับ
- **อ่านร้อยรีวิวแล้วยังไม่รู้อะไร** — เพราะรีวิวจริงส่วนใหญ่เป็นแบบผสม (*"ของดีแต่ส่งช้า"*)
  การสรุปเป็นบวก/ลบขั้วเดียวจึงทิ้งข้อมูลที่คนซื้อต้องการที่สุดไป

**สิ่งที่ระบบทำ 3 ขั้น:**

```
รีวิวดิบ
   │
   ├─ ① คัดกรอง      ลบข้อมูลติดต่อ แล้วใช้ "สิ่งที่ลบไป" เป็นสัญญาณจับสแปม
   │                  →  คะแนนความน่าเชื่อถือ 0–100 + สถานะ ผ่าน/น่าสงสัย/สแปม
   │
   ├─ ② สกัดข้อมูล    แบรนด์ · ร้านค้า · ราคา · วันจัดส่ง · ขนส่ง · สี/ไซส์ · สถานที่
   │
   └─ ③ Aspect-Based  แยกเป็น 6 ด้าน แล้วบอกว่าด้านไหน "ชม" ด้านไหน "ติ"
                      →  ตอบได้ว่า "ของดีแต่ส่งช้า" ไม่ใช่แค่ "รีวิวนี้กลาง ๆ"
```

**จุดที่ตั้งใจออกแบบให้ต่าง:** โดยทั่วไป Regex cleansing เป็นแค่ขั้นตอน "ล้างข้อมูลทิ้ง"
แต่ที่นี่ข้อมูลที่ถูกลบ (เบอร์โทร / LINE ID / URL) กลายเป็น **ฟีเจอร์หลักของโมดูลคัดกรอง**
เพราะเบอร์โทรในรีวิวสินค้าแทบไม่มีเหตุผลอื่นนอกจากการโฆษณาแฝง

### Aspect ทั้ง 6 ด้าน

| ด้าน | ตัวอย่างคำชม | ตัวอย่างคำติ |
|---|---|---|
| 🔧 คุณภาพสินค้า | ทน, แข็งแรง, งานดี, ของแท้ | พัง, ชำรุด, ของปลอม, ใช้ไม่ได้ |
| 🎯 ความตรงปก | ตรงปก, ตรงตามที่สั่ง | ไม่ตรงปก, สีเพี้ยน, ผิดไซส์ |
| 💰 ราคา / ความคุ้มค่า | คุ้ม, ถูก, ราคาดี | แพง, ไม่คุ้ม, เสียดายตังค์ |
| 🚚 การจัดส่ง | ส่งไว, ส่งตรงเวลา | ส่งช้า, ของหาย, รอนาน |
| 📦 บรรจุภัณฑ์ | แพ็คแน่น, ห่ออย่างดี | กล่องบุบ, กล่องยับ, แพ็คห่วย |
| 🧑‍💼 บริการร้านค้า | ตอบไว, บริการดี, แถมของ | ไม่ตอบ, ไม่รับผิดชอบ, เคลมยาก |

## วิธีใช้งาน

แอปมี 3 แท็บ

### 📝 แท็บ 1 — วิเคราะห์รีวิวเดี่ยว

1. เลือกตัวอย่างจาก dropdown (มี 6 แบบ: รีวิวผสม, สแปม, รีวิวยาว, คำลากเสียง, รีวิวสั้น, ภาษาอังกฤษ)
   หรือพิมพ์/วางข้อความเอง — **ระบบตรวจภาษาให้อัตโนมัติ**
2. กดปุ่ม **วิเคราะห์**
3. อ่านผลลัพธ์:
   - **แถบสถานะ** — ผ่าน / น่าสงสัย / สแปม พร้อมคะแนนความน่าเชื่อถือ
   - **เหตุผลที่หักคะแนน** — บอกทุกข้อว่าหักเพราะอะไร กี่คะแนน
   - **ข้อมูลที่สกัดได้** — ราคา, วันจัดส่ง, แบรนด์, ร้าน, ขนส่ง, สถานที่, สี/ไซส์
   - **วิเคราะห์ราย aspect** — 6 ด้าน พร้อม**คำที่ใช้ตัดสิน** เพื่อให้ตรวจสอบได้ว่าระบบดูจากอะไร
   - **🔬 ดูขั้นตอนการประมวลผลทั้งหมด** — กางดู raw → clean → normalized → tokens → POS ได้ทีละขั้น

> 💡 ในแถบข้างมีสวิตช์ **เปิดตัวตรวจคำสะกดไทย** — แม่นขึ้นกับคำพิมพ์ผิดที่ไม่อยู่ในตาราง
> แต่ช้าลงมาก จึงแนะนำให้เปิดเฉพาะตอนวิเคราะห์รีวิวเดี่ยว

### 📊 แท็บ 2 — วิเคราะห์หลายรีวิว

1. กด **📂 ใช้ชุดข้อมูลตัวอย่าง** (544 รีวิวที่มากับระบบ) หรืออัปโหลด CSV ของตัวเอง
2. เลือกคอลัมน์ที่เก็บข้อความรีวิว (ระบบเดาให้ก่อน) และจำนวนรีวิวที่จะวิเคราะห์
3. กด **เริ่มวิเคราะห์**
4. ได้ผลสรุป:
   - จำนวนรีวิวที่ผ่าน / น่าสงสัย / สแปม, ช่วงราคา, ระยะเวลาจัดส่งเฉลี่ย
   - **ตารางสรุปราย aspect** + กราฟแท่งชม/กลาง/ติ
   - **คำชม / คำติที่พบบ่อย**
   - **TF-IDF Keywords** และ **LDA Topic Modeling** (ปรับจำนวนหัวข้อได้ 3–8)
   - **ตารางผลลัพธ์รายรีวิว** กรองตามสถานะและตาม aspect ได้
   - ปุ่ม **⬇️ ดาวน์โหลดผลลัพธ์เป็น CSV**

**รูปแบบ CSV ที่อัปโหลดได้:** ขอแค่มีคอลัมน์ข้อความ 1 คอลัมน์
ถ้ามีคอลัมน์ `review_id` และ `product_name` ด้วย ระบบจะใช้ประโยชน์เพิ่ม

```csv
review_id,raw_text,product_name
R001,ของดีมากค่ะ ส่งไวด้วย,หูฟังบลูทูธ
R002,กล่องบุบมาเลย แต่ของยังใช้ได้,ลำโพงพกพา
```

### เหตุผลเบื้องหลังการออกแบบ

ทุกข้อด้านล่างมาจากปัญหาที่**เจอจริงตอนทดสอบ** ไม่ใช่การเดาล่วงหน้า

**1. ต้อง normalize ก่อน tokenize**
PyThaiNLP ตัด `"ส่งไวมากกกกก"` เป็น `['ส่ง','ไว','มาก','กก','กก']`
แต่ถ้ายุบคำลากเสียงก่อนจะได้ `['ส่ง','ไว','มาก']` ตามที่ควรเป็น

**2. ห้ามค้นคำแบบ substring ในภาษาไทย**
ภาษาไทยไม่เว้นวรรค ทำให้ `"ทน"` (ทนทาน) ไปแมตช์กลางคำ `"ตัวแทน"`
และ `"เลย"` (จังหวัดเลย) ไปแมตช์ใน `"ได้เลยค่ะ"`
→ ระบบจึงค้นบนข้อความที่ตัดคำแล้ว โดยบังคับให้แมตช์ต้อง**เริ่ม**ที่ขอบเขตคำ

**3. ขอบเขตคำปฏิเสธต้องวัดด้วยจำนวนคำ ไม่ใช่ระยะตัวอักษร**
ในประโยค `"ยังไม่มีปัญหาเลย ทนกว่าตัวเก่า"` คำว่า `"ไม่"` เป็นของ `"มีปัญหา"`
ไม่ใช่ของ `"ทน"` ที่อยู่ห่างไป 2 คำ — การวัดด้วยระยะตัวอักษรทำให้พลิกขั้วผิด
(แก้แล้วความถูกต้องของขั้วเพิ่มจาก 82.8% เป็น **85.9%**)

**4. แก้คำพิมพ์ผิดต้องทำระดับโทเคน ไม่ใช่ `str.replace()`**
กฎ `"ไร" → "อะไร"` ทำให้ `"ไม่เป็นไร"` กลายเป็น `"ไม่เป็นอะไร"` ถ้าแทนที่ทั้งข้อความ

**5. ใช้ทั้ง Regex และ NER คู่กัน**
spaCy มอง `"6195"` ใน `"the inverter costs Rs. 6195"` เป็น `DATE` ไม่ใช่ `MONEY`
แต่ regex ราคาจับถูก — ส่วน NER เก่งกว่าตรงชื่อเฉพาะที่เขียนได้หลายแบบ
(และ regex เองก็ต้องระวัง: `rs` ที่ไม่มีขอบเขตคำจะไปแมตช์ท้ายคำ `"service centers 2"`)

**6. คำชมกลาง ๆ ไม่ควรผูกตายกับ aspect ใด**
`"ประทับใจ"` ใช้ชมด้านไหนก็ได้ — `"ประทับใจร้านนี้"` คือบริการ ไม่ใช่คุณภาพสินค้า
→ เก็บคำเหล่านี้แยก แล้วโยงเข้ากับ aspect ที่อยู่ใกล้ที่สุดในข้อความ

**7. ต้องกันคำในโดเมนจากการลบ stopwords**
stopword list ของ PyThaiNLP มี `"ส่ง"`, `"ราคา"`, `"ดี"` อยู่ด้วย ซึ่งเป็นคำชี้ aspect ที่ระบบขาดไม่ได้

## ชุดข้อมูลทดสอบ

| ไฟล์ | จำนวน | ที่มา |
|---|---|---|
| `data/reviews_flipkart_en.csv` | 500 | สุ่ม stratified จาก [Flipkart Product Reviews](https://www.kaggle.com/datasets/niraliivaghani/flipkart-product-customer-reviews-dataset) (205,052 แถว) |
| `data/reviews_th.csv` | 44 | **เขียนขึ้นเอง** พร้อมกำกับ `expected_aspects` เป็น ground truth |
| `data/reviews_sample.csv` | **544** | รวมสองชุด — ไฟล์ที่แอปโหลด |
| `data/en_vocab.txt` | 1,866 คำ | คลังคำอังกฤษที่สร้างจาก corpus เต็ม ใช้แยกคำที่ติดกัน |

**ทำไมต้องเขียนชุดไทยเพิ่ม:** ชุด Flipkart ผ่านการ moderate มาแล้ว
**ไม่มี URL เลยสักแถว และมีเบอร์โทรเพียง 2 แถวจาก 205,052**
ถ้าใช้ชุดนั้นอย่างเดียวจะทดสอบโมดูลคัดกรองสแปมไม่ได้เลย

**สิ่งที่พบจากชุดข้อมูลต้นฉบับ (และวิธีรับมือ):**
- มี 3 แถวที่คอลัมน์เลื่อน → ตรวจจับด้วย `Rate` ที่ไม่ใช่ 1–5 แล้วตัดทิ้ง
- `product_name` มี mojibake → ล้างด้วย regex
- **เครื่องหมายวรรคตอนถูกลบไปหมด** ทำให้คำติดกัน (`"productfeel"`, `"acbut"`)
  → สร้างคลังคำจาก corpus เต็ม แล้วตัดคำติดกันแบบอนุรักษ์นิยม (แตะเฉพาะคำที่ไม่มีในคลัง)
- `Sentiment` label มี noise (เจอแถว `rate=4` แต่ label `negative`) → ใช้เทียบเป็นแนวโน้ม ไม่ใช่ค่าชี้ขาด

การกระจายตัวหลังสุ่ม: positive 193 / negative 183 / neutral 158 / mixed 10 · ความยาว median 101 ตัวอักษร

## ผลการประเมิน

รันด้วย `python scripts/evaluate.py` (544 รีวิว, ~13 วินาที, **23 ms/รีวิว**)

### ความแม่นยำของ Aspect (เทียบ ground truth ที่กำกับเองในชุดไทย)

| ตัวชี้วัด | ค่า |
|---|---|
| Precision | **84.2%** |
| Recall | **80.0%** |
| F1 | **82.1%** |
| ความถูกต้องของขั้ว (ชม/ติ/กลาง) | **85.9%** (55/64) |

### เคสคัดกรองที่ตั้งใจทดสอบ

| เคส | ผล |
|---|---|
| จับโฆษณาแฝง | ✅ 4/4 |
| จับรีวิวซ้ำ | ✅ 3/3 |
| ลบเบอร์โทร / LINE ID / URL / อีเมล | ✅ 2/2 ทุกประเภท |
| ยุบคำลากเสียง | ✅ 47/47 |
| ดึงราคา | ✅ 37/37 |
| ดึงจำนวนวันจัดส่ง | ✅ 55/56 |
| ตรวจพบ HTML | ✅ 1/1 |
| วิเคราะห์ข้อความไทยปนอังกฤษ | ✅ 4/4 |
| จับรีวิวคุณภาพต่ำ | ⚠️ 58/67 |

### เทียบ `overall_sentiment` กับ label ของ Flipkart

ตรงกัน **65.4%** (327/500) — ตัวเลขนี้ต่ำโดยตั้งใจ เพราะระบบมีคลาส `mixed` เพิ่มมา
ในขณะที่ Flipkart บังคับให้ทุกรีวิวเป็น positive/neutral/negative เท่านั้น
รีวิวแบบ *"ของดีแต่ส่งช้า"* จึงถูกนับว่า "ไม่ตรง" ทั้งที่ระบบตอบละเอียดกว่า
ประกอบกับ label ต้นทางเองก็มี noise จึงควรอ่านเป็นแนวโน้ม ไม่ใช่ค่าชี้ขาด

### ข้อจำกัดที่รู้ตัว

- รีวิว 26% ไม่พบ aspect ใดเลย — ส่วนใหญ่เป็นรีวิวสั้นทั่วไป (`"nice"`, `"super"`) ซึ่งไม่มี aspect จริง ๆ
- ใช้ lexicon ไม่ใช่โมเดล ML → คำใหม่/คำแสลงที่ไม่อยู่ในพจนานุกรมจะจับไม่ได้
  (แลกมากับการที่**อธิบายได้ทุกขั้นตอนว่าตัดสินจากคำไหน** และไม่ต้องมีข้อมูลเทรน)
- ประโยคเงื่อนไข (`"ถ้าเป็นของแตกง่ายคงพัง"`) ยังถูกนับเป็นคำติ

## ตัวอย่าง Prompt ที่ใช้สั่ง AI

โปรเจกต์นี้พัฒนาโดยใช้ AI ช่วยเขียนโค้ด ตัวอย่าง prompt ที่ใช้จริง

### 1. ออกแบบหัวข้อและ schema

```
โจทย์คือทำ Streamlit web app ประมวลผลข้อความไทย/อังกฤษ ต้องใช้เทคนิค
Regex & Cleansing, Tokenization & Normalization, Topic Identification, POS & NER
ให้ครบ ผมเลือกหัวข้อ "รีวิวสินค้า"
ช่วยออกแบบ schema ผลลัพธ์ว่าจะสกัดฟิลด์อะไรบ้าง
โดยแต่ละฟิลด์ต้องระบุว่าใช้เทคนิคไหนสกัด และยกตัวอย่างค่าจริงประกอบ
```

### 2. เตรียมชุดข้อมูลทดสอบ

```
เตรียมไฟล์ข้อมูลทดสอบจาก dataset นี้
kagglehub.dataset_download("niraliivaghani/flipkart-product-customer-reviews-dataset")
ให้สำรวจข้อมูลก่อนว่ามี noise แบบไหนบ้าง แล้วค่อยสุ่มตัวอย่างแบบ stratified
ที่ครอบคลุมทุกเคสที่ระบบต้องรับมือ ไม่ใช่สุ่มธรรมดา
```

> AI สำรวจแล้วพบว่า dataset ไม่มี URL เลยสักแถว จึงเสนอให้เขียนชุดรีวิวไทยเพิ่ม
> เพื่อให้ทดสอบโมดูลคัดกรองสแปมได้ — เป็นข้อเสนอที่มาจากการดูข้อมูลจริง

### 3. เขียนโมดูลตามหลักการที่กำหนด

```
เขียนโมดูล aspect-based sentiment ที่รองรับทั้งไทยและอังกฤษ
ต้องจัดการคำปฏิเสธ ("ไม่คุ้ม" ต้องเป็นลบ ไม่ใช่บวก)
และต้องอธิบายได้ว่าตัดสินจากคำไหน เพื่อให้ผู้ใช้ตรวจสอบย้อนกลับได้
แยกตรรกะออกจาก UI ให้ทดสอบได้โดยไม่ต้องเปิดเว็บ
```

### 4. หาสาเหตุบั๊กจากผลการประเมิน

```
ผลประเมินบอกว่า aspect "คุณภาพ" ทายขั้วผิดเป็นลบ ทั้งที่ ground truth เป็นบวก
ในรีวิว "ยังไม่มีปัญหาเลย ทนกว่าตัวเก่า"
ช่วยหาสาเหตุจริงจากโค้ด อย่าเดา และอย่าแก้ด้วยการเพิ่มคำใน lexicon
ถ้าต้นเหตุอยู่ที่ตรรกะ
```

> ผลคือพบว่าขอบเขตของคำปฏิเสธวัดด้วย "ระยะตัวอักษร" ซึ่งทำให้ `"ไม่"` ของ `"มีปัญหา"`
> ไปพลิกขั้วของ `"ทน"` ที่อยู่ห่างไป 2 คำ → แก้เป็นวัดด้วยจำนวนคำที่คั่นกลาง

### 5. ตรวจว่าแอปรันได้จริงก่อน deploy

```
ใช้ streamlit.testing.v1.AppTest กดปุ่มจริงทุกปุ่มในแอป
เพื่อจับ runtime error ก่อน deploy อย่าเช็คแค่ว่า server ขึ้น
```

### บทเรียนจากการใช้ AI ในโปรเจกต์นี้

- **สั่งให้สำรวจข้อมูลก่อนเขียนโค้ด** ทำให้เจอปัญหาที่คาดไม่ถึง เช่น เครื่องหมายวรรคตอนถูกลบไปหมด
- **สั่งให้หาสาเหตุจริง ห้ามเดา** ได้ผลดีกว่าสั่งให้ "แก้ให้หน่อย" เพราะ AI มักแก้ปลายเหตุด้วยการเพิ่มคำใน lexicon
- **ให้เขียนสคริปต์ประเมินผลไว้ตั้งแต่แรก** ทำให้รู้ทันทีว่าการแก้แต่ละครั้งทำให้ดีขึ้นหรือแย่ลง
- **ต้องตรวจงานของ AI เสมอ** — บั๊กหลายตัวในโปรเจกต์นี้ (การแทนที่คำพิมพ์ผิดแบบ substring,
  `rs` ที่ไม่มีขอบเขตคำ) มาจากโค้ดที่ AI เขียนเอง และเจอเพราะมีการทดสอบเทียบ ground truth
